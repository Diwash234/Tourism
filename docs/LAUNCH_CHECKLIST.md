# Launch checklist

Grounded in what this repository actually checks, not in aspirations. Every
"blocked on you" item is something no code change can supply.

Regenerate the machine-checkable part with:

```bash
cd Tourism
python manage.py validate_production_config
```

It exits non-zero while any critical item is unmet, and it never prints a
secret value.

## 1. Blocking: the published release artifact was stale

**Status: being repaired by rebuilding it.** The tracked
`downloads/nepal-tourism-database.sqlite3.gz` and
`dataset/verified_tourism_data.json` were built before two separate changes:

- new model columns (media-review provenance, `elevation_m`), so the exporter
  could not re-read its own release database;
- a CMS publication change (`0081_unpublish_seeded_cms_placeholders`), so the
  rebuild no longer contained the sections the artifact listed.

Either drift made the "Verify published data artifact" CI step fail, and no
code fix can reconcile a semantic change with an old artifact. The repair is a
release rebuild, which changes what every public download link serves. The
tolerance added in `336799c` stops the *schema* class of drift from recurring;
the rebuild clears the semantic one.

Note: this was already red on `main` before the media-review commit
(`abccedf` fails identically on `elevation_m`).

## 2. Blocking: environment configuration

All of these are deployment inputs, not code. `validate_production_config`
currently reports them as failures:

| Item | Why it blocks |
| --- | --- |
| `DEBUG=False` | debug traces and stack pages must not reach users |
| `SECRET_KEY` (>=50 chars, not a placeholder) | signs sessions; a shared dev key means anyone can forge a session |
| `ALLOWED_HOSTS` (explicit, not `*`) | `*` with `DEBUG=False` enables host-header abuse |
| `ML_SERVICE_API_KEY` | the ML service is unauthenticated without it |
| `ML_WEBHOOK_SECRET` | inbound ML webhooks are forgeable without it |
| `EMAIL_BACKEND` (not console) | console email backend means no verification or reset mail is ever delivered |
| `ROUTING_API_URL` | without it navigation cannot claim verified road routing, and the app says so |

And the warnings worth clearing:

- `SESSION_COOKIE_SECURE` — auto-enabled when `DEBUG=False`; verify the reverse
  proxy actually terminates HTTPS.
- Backups — run `manage.py backup_database` and confirm archives exist. A
  launch without a restore you have tested is not a launch.
- OAuth — see below.

## 3. OAuth provider credentials — blocked on you

Real Google and GitHub client credentials cannot be generated by this
application; they require your own provider accounts.

What the code now does for you:

- `validate_production_config` **fails** if a provider is half-configured
  (client id without a secret, or a placeholder value). Previously a client id
  alone was reported as "credentials present" and only failed at runtime during
  the authorization-code exchange.
- It **warns**, not fails, when a provider is simply unset, because social
  sign-in is legitimately optional and the UI already keeps the buttons
  disabled rather than faking a login.
- It prints the exact callback URIs to register:
  `<FRONTEND_ORIGIN>/auth/callback/google` and `.../auth/callback/github`.
  Registering the wrong URI fails silently at runtime otherwise.

To finish: create the credentials in Google Cloud Console and GitHub Developer
Settings, set `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` and
`GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET`, and register those callback URIs.

## 4. Database

`validate_production_config` reports the current SQLite file as
"WAL-hardened, production-viable on a single node" and recommends Postgres
(`DATABASE_URL`) for more than one instance. That is a capacity decision, not a
code defect. Before launch, apply every migration:

```bash
python manage.py migrate
python manage.py migrate --check   # must be a no-op
```

## 6. Live weather — built; official alert feeds — deliberately not scraped

**Weather is implemented and verified against the live API.** `weather_service.py`
uses Open-Meteo's `/v1/forecast`, which needs **no API key**, and was checked
end to end: a real Kathmandu reading (22.8 °C, gusts 28.8 km/h, "Slight rain
showers"), a 3-day forecast, caching, and refusals for null-island coordinates.
19 tests cover the contract.

Two constraints you must know before launch:

- The free Open-Meteo tier is **non-commercial only** (~10,000 calls/day) and
  carries **no uptime guarantee**. Commercial use needs a customer-prefixed URL
  and an API key. Every provider failure returns `available: false` with a
  reason; nothing is ever substituted or invented.
- It is a **model forecast**, not a station observation, and the response says
  so (`kind: "model_forecast"`). Do not present it as a local measurement.

**Official alerts are not implemented, and that is deliberate.** The Department
of Hydrology and Meteorology (dhm.gov.np) publishes forecasts and early
warnings on its website and in its "Nepal Weather Official" app, but exposes
**no documented public API or feed**. Scraping an undocumented government site
would be fragile and would present scraped text as a verified official alert,
which is exactly the claim this project refuses to make. When a permitted,
documented feed exists, wire it through the same provider pattern
(`weather_provider` SiteSetting, HTTPS-only, cached, honest unavailable state).

## 7. Media review — on `main`, needs a policy decision

The canonical release gate is configurable
(`PUBLIC_SNAPSHOT_MEDIA_GATE=scored|approval`); the default preserves current
behaviour. Nothing fabricates a score, and reviewer identity never ships in a
public release. Before launch, choose a gate and record it.

Measured on the **seed** database (`nepal-tourism-seed.sqlite3.gz`, 14,861
gallery rows), not on the release source: the `scored` gate with provenance
required yields **0** eligible images, because the imported data has no
attributed review; the `approval` gate yields **1,146**. If you publish under
`scored`, expect the image count to fall to zero until a reviewer has actually
reviewed media — that is the rule working, not a bug.

## 8. Placeholder service coordinates — repairable, but the geocoder is the constraint

`audit_coordinates` reports 808 bad rows on the real dataset. The root cause is
bulk-imported data: all 491 hospital and 958 police coordinates (**1,449
rows**) carry no `coordinate_source`, so nothing downstream can tell a real
position from an inherited one. 317 hospitals and 385 police stations share a
coordinate with a peer row; a further 17 and 9 are byte-identical to their own
parent destination's pin.

`manage.py geocode_placeholders` repairs this and records provenance
(`coordinate_source` / `coordinate_status` / `coordinate_retrieved_at`,
migration 0088). It is dry-run unless `--apply`, single-threaded, cached,
resumable, and never overwrites a coordinate that already names a source.

**Do not point it at the public Nominatim for the full batch.**
<https://operations.osmfoundation.org/policies/nominatim/> asks for at most 1
request/second, requires an identifying User-Agent and visible OpenStreetMap
attribution, and states that "bulk geocoding of larger amounts of data is not
encouraged" — recurring jobs are capped at 4 requests/minute. 1,449 rows at the
policy interval is ~27 minutes of sustained requests, i.e. precisely the bulk
case. The command warns above 50 rows and points at the alternative.

To actually clear this, pick one:

- run your own Nominatim instance (needs its own PostgreSQL + OSM extract; pass
  `--base-url` or set `GEOCODER_BASE_URL`) — free but the setup is real work;
- a commercial geocoder with bulk terms that permit it;
- or hand-review the highest-value rows — the "far" ones (95) and the ones whose
  address text reads like a generator note are the ones actually hurting
  "nearest hospital" answers.

Re-run `audit_coordinates` afterwards: it now prints provenance coverage per
model, so the improvement is measurable rather than assumed.
